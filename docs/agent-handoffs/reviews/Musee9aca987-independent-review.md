## Findings, ranked

1. **High — stale ownership evidence can delete a preexisting container.** `harness/supervise.sh:91` loads any existing `owned-containers.txt`; `:104`–`:106` removes its IDs without binding the record to the new job or excluding IDs already in `BEFORE_ALL`. The shim appends at `harness/bin/docker:23`, and the supervisor neither creates a fresh exclusive ownership file nor rejects a reused staging root. Reproduction with the exact supervisor and package stubs: seed a preexisting fake container ID in both baseline state and an old ownership file, then run a fixture that creates no container. Cleanup removes that preexisting fake container and records `container_cleanup: PASS`. Use a fresh job-specific ownership record, reject stale/shared roots, and verify each cleanup target against current-job creation provenance and baseline membership before removal. A BLOCKED final result does not undo an unrelated deletion.

2. **High — the hard deadline is disabled precisely when process identity is uncertain.** `harness/supervise.sh:198`–`:201` stops the unit only when `IDENTITY=PASS`; missing/mismatched `job.json` allows the workload to continue. `:223` then waits without a bound. The host-config loop's time check does not bound the later wait. Reproduction: package stubs, fixture sleep 60 seconds, configured hard deadline 1 second. Identity is UNKNOWN under the documented stub topology; the supervisor remains live after 6 seconds and has no cleanup evidence, until the independent test controller kills its synthetic process group. Establish authoritative ownership of the unit at launch and always enforce a bounded stop on that owned unit; an identity failure should trigger fail-closed cleanup, not disable cancellation. Also bound Docker/systemctl inspection calls: several ps/show/inspect calls can otherwise hang before reaching the watchdog or cleanup.

3. **High — failed baseline inspections are hidden by pipelines, so the harness starts after a daemon failure.** `harness/supervise.sh:38` enables nounset but not pipefail. The `docker ps | sort` pipelines at `:58` and `:60`, and `ls | sort` at `:63`, return sort's success rather than the inspection failure. The same problem affects cleanup observations at `:94` and `:122`. Reproduction with `STUB_DOCKER_MODE=down`: the exact supervisor records `baseline: PASS`, launches the fixture (`launcher.pid` exists), and ultimately returns BLOCKED only because other components are unknown. The shipped E1 assertion at `tests/run-regression.sh:153` checks that eventual BLOCKED status but never checks the baseline or whether a launcher ran, despite printing “nothing launched.” Enable pipefail or capture each inspection separately and assert launch absence on baseline failure. Test cleanup inspection failures as well.

4. **High — a systemd scope cannot install the requested execution sandbox.** `harness/supervise.sh:153` selects `systemd-run --scope`, then requests service execution properties `PrivateNetwork`, `ProtectSystem` and `ReadWritePaths` at `:154`–`:156`. Scopes manage externally created processes and resource controls; they do not create service execution namespaces/mount sandboxes. Depending on the systemd interface/version, unsupported properties are rejected or the requested sandbox is absent. The inside check should prevent the runner import when absent, but there is no demonstrated valid path to the claimed confined run. Use an appropriate transient service or independently reviewed namespace launcher, then validate its effective restrictions before importing the runner. The check at `harness/confinement-check.mjs:28`–`:51` also verifies only selected filesystem/network/memory observations; CPU quota, PID cap and the complete writable-path policy remain unverified. This finding is source/semantics review, not a real systemd execution test.

5. **Medium — containment and mtime do not establish temporary-file ownership.** `harness/supervise.sh:124`–`:134` deletes every new entry in STAGE_TMP if its resolved location is a direct child and its mtime is recent. Another writer's new file meets both conditions. Reproduction: during an otherwise normal synthetic fixture run, the independent controller creates `STAGE_TMP/unrelated-new-artifact`; cleanup deletes it and reports `tmp_cleanup: PASS`. Use a job-private directory created exclusively by the supervisor and remove only that owned directory; refuse shared/reused or symlinked roots. Preserve and report unrelated entries rather than deleting them. The existing checks do not establish the “ownership” claimed by the comments.

6. **Medium — attached Docker output is mistaken for creation identity.** `harness/bin/docker:17` waits for the complete command output, and `:20`–`:23` treats the last 64-hex line from either create or run as the owned container ID. For ordinary attached `docker run`, stdout is workload output, not the container identity; a 64-hex workload line can be recorded as another cleanup target. Capture is also delayed until command termination, so a hung/killed attached run can leave no ownership record for its actual container. Use a protected per-job Docker cidfile or explicit create/start protocol, then inspect/validate the recorded identity before cleanup. Independently executed a synthetic executable returning only a 64-hex log line for `run`: the exact shim exited 0 and recorded that log line as an owned ID. No daemon was involved.

## Other review observations and limitations

The confined launcher calls the checker before the preload/runner import, which is a useful fail-closed ordering; its real sandbox and file-cap behavior were not exercised by the fixture launcher.

The root reviewer separately reported a score-contract mismatch in `run-scan-once.mjs` against the underlying runner; this reviewer has not independently read that underlying contract and does not count the root's probe as independently executed validation here.
