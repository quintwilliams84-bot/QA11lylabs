## Findings, ranked

1. **High — failed launch can stop a unit the supervisor did not create.** `harness/supervise.sh:41` derives the unit name from the supplied run ID. On launch failure, `:261`–`:265` still enters cleanup; `:219` invokes the unconditional `stop_unit` at `:102`. There is no successful-launch ownership flag, manager invocation identity or preexisting-unit exclusion. If a unit already exists with that name and systemd rejects the new launch, cleanup stops the existing unit. Independently reproduced using the exact supervisor with a fake launch-collision response and package systemctl stub: a preexisting synthetic sleep process associated with the unit name was terminated; supervisor exit 4. Stop/kill/reset-failed must apply only to a unit proven to belong to this supervisor invocation. A fresh filesystem root does not establish manager-unit ownership.

2. **High — failed unit inspections become cleanup PASS.** `harness/supervise.sh:221` starts UNIT_CLEAN at PASS; `:222` treats every nonzero `systemctl is-active` result as proof of inactivity, including permission errors, manager failure and timeout. A previously sampled dead/absent MainPID at `:225` does not prove the unit's cgroup is empty or that a replacement main process is absent. Stop errors are swallowed at `:102`. Independently executed the exact cleanup function against fake Docker inventory and fake systemctl returning exit 1 for all operations. It recorded UNIT_CLEAN, CONTAINER_CLEAN and TMP_CLEAN as PASS; with other components set to PASS, the exact aggregator returned `PASS 0`. This is an isolated synthetic component/aggregation reproduction, not a real-service pass. Capture manager status explicitly, distinguish verified inactive/not-found from failed inspection, and verify the owned invocation/cgroup termination. Missing observation must remain UNKNOWN/BLOCKED.

3. **High — HostConfig checks the wrong resource field and can retain PASS after later inspection failure.** `harness/supervise.sh:332` requests Memory, **MemorySwap**, and PidsLimit, then `:334` compares the middle field to 1,000,000,000. That value previously represented NanoCpus for a one-CPU bound; NanoCpus is never inspected here. An unlimited-CPU container can satisfy this comparison if its swap limit has that value; a correctly bounded container with another swap configuration can fail. In addition, `:332` turns failed inspections into an empty string and `:333` simply skips them, preserving any earlier HOSTCONFIG PASS. The global PASS also does not establish every owned container was inspected before completion. Verify the intended memory/CPU/PID fields, track evidence per created container, and fail closed on unavailable/failed observations. The shipped Docker stub returns a generic HostConfig triple regardless of the requested fields (`tests/stubs/bin/docker:39`), so its happy-path assertion cannot catch this field substitution. This finding is source inspection; no real Docker call was made.

4. **High — service failure can be hidden by a PASS result file.** `harness/supervise.sh:357`–`:364` derives HARNESS solely from result.json once the local watchdog has not fired. It never obtains or checks the manager's ExecMainCode/ExecMainStatus/Result, so a workload that writes a PASS result and subsequently crashes, is externally killed or fails during final output can still contribute HARNESS PASS. `run-confined.sh:32` preserves the harness exit status, but the supervisor never consumes that status. Require the exact owned service invocation's successful terminal status as well as complete result evidence before HARNESS can PASS. This is source review, not independently exercised real-service behavior.

5. **Medium — assembly digest does not bind symlinks or executable modes.** `harness/supervise.sh:107` hashes only entries selected by `find . -type f`; `:122` copies the full tree with cp -a, including symlinks and their metadata. Independently executed the exact tree_digest function on a synthetic tree: changing a symlink to another temporary target and changing a regular file's executable mode left the digest unchanged. A symlinked input can therefore change after assembly verification while ASSEMBLY remains PASS. Reject escaping/unresolved symlinks and unsupported file types, and bind an explicitly defined canonical tree including relevant modes and link targets. If internal links are permitted, verify their complete resolved closure and preserve it in the copied tree. This matters separately from the packaging fix, which correctly preserves the package scripts' executable bits.

6. **Medium — standalone pairing preflight can PASS without host/run bindings.** `pairing/preflight-verify.mjs:119`–`:120` checks host/run equality only when the respective CLI argument is supplied; `:121`–`:124` does not require either record field. Independently ran the exact verifier with a synthetic matching manifest/browser/image and approval record containing no host_id or run_id, omitting those CLI flags: exit 0, pairing-gate PASS, OVERALL PASS. Require nonempty expected host/run arguments and matching nonempty record fields. The runtime harness does require these values at `harness/run-scan-once.mjs:98`–`:99`, and the runbook supplies the flags, so this is an incorrect standalone preflight claim rather than a demonstrated bypass of the downstream runtime gate.
